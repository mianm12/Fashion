# 基于 H&M 交易数据与商品属性层次图的周级流行趋势预测与轻量 Top-N 推荐课题调研报告

## 结论摘要

围绕 H&M 在 Kaggle 发布的竞赛数据，把问题重构为“周级属性趋势预测 + 轻量 Top-N 推荐”，结论是：**可行，但必须收缩问题边界**。这个方向比“知识图谱 + 复杂推荐 + 多任务端到端联合学习”更适合本科毕设，因为数据本身天然包含时间序列交易与较丰富的商品元数据，官方任务又正好是未来 7 天购买预测与 MAP@12 评价；同时，公开高分方案普遍采用“候选召回 + 排序”的两阶段思路，而且非常依赖 recent popular items 与轻量排序模型，而不是重型端到端图模型。换句话说，你的设想不是“降级版 Kaggle”，而是把竞赛问题转译成一个更利于复现、解释和答辩的研究问题。

从研究价值上看，这个课题也成立。时尚推荐研究本来就同时覆盖 item recommendation 与更广义的 fashion prediction tasks；而时尚趋势研究中，也已经存在“预测 style/attribute 的未来流行度”“利用属性时间序列作为流行度代理”的文献路线。你如果把“属性级周趋势预测”作为主任务，把“趋势感知 Top-N 推荐”作为辅任务或应用展示，既能接住推荐系统方向，也能体现一点时尚趋势建模的研究味道。

| 判断项 | 结论 | 建议 |
|---|---|---|
| 课题总判断 | **可行但需收缩** | 不做重型端到端联合模型 |
| 是否适合本科毕设 | **适合** | 强调“可复现 + 可解释 + 可答辩” |
| 是否适合只用 H&M 数据集完成 | **适合** | 不需要额外社媒/图像数据也能成题 |
| 主任务 | **属性级周趋势预测** | 比商品级更稳、更易解释 |
| 辅助任务 | **轻量 Top-N 推荐** | 作为应用展示和性能验证 |
| 图结构命名 | **商品属性层次图** | 方法章节可补充“异构图”表述 |
| 最终推荐模块 | **候选召回 + 轻量重排序** | 首选线性重排或 LightGBM Ranker |
| 不建议作为主线的内容 | **复杂 KG、双塔、重型 GNN、端到端联合多任务** | 容易失控、答辩风险高 |

如果只给一个最稳妥版本，我的建议是：**把论文核心写成“基于商品属性层次图的周级服装属性趋势预测”，再把推荐写成趋势的应用展示与增益验证**。这样最容易把论文结构、实验方案和答辩话术统一起来。

## 课题定位与题目建议

你的原始题目方向是对的，但“商品属性层次图”比“知识图谱”更稳妥，“周级流行趋势预测”最好明确为“属性级趋势”，而“轻量 Top-N 推荐”非常适合放在副标题或方法后半段。原因是：真正的电商知识图谱案例往往会引入外部实体、显式 ontology、三元组关系抽取与实体链接；而你手头这个数据集主要是内部商品分类与属性元数据，更像一个**商品分类-属性-商品**结构化图，而不是严格意义上需要被答辩老师追问本体设计的知识图谱。

ACM 的时尚推荐综述也表明，fashion recommendation 并不只等于“搭配推荐”或“图神经网络推荐”，它同样包括 item recommendation 与其他 fashion prediction tasks。你用“趋势预测主、推荐辅”的方式来组织论文，从学术表达上是说得通的。

| 版本 | 推荐题目 |
|---|---|
| 稳妥本科版 | **基于 H&M 交易数据的周级服装属性趋势预测与轻量 Top-N 推荐** |
| 学术论文版 | **基于商品属性层次图的周级服装属性趋势预测与趋势感知 Top-N 推荐研究** |
| 简洁答辩版 | **H&M 服装周趋势预测与轻量推荐方法研究** |

| 表述术语 | 适用场景 | 风险 | 论文中的建议用法 |
|---|---|---|---|
| 知识图谱 | 有外部知识、本体、三元组、实体链接 | 容易被追问 ontology、关系语义、图谱补全 | **不建议放在标题中** |
| 商品属性层次图 | 商品分类层级 + 颜色/图案/风格属性分支 | 风险最低 | **标题首选** |
| 商品属性异构图 | 多节点类型、多边类型、含 item-attribute/item-item 边 | 术语稍“技术化” | **方法章节可用** |
| 知识图谱式商品表示 | 想说明受 KG 启发，但并非严格 KG | 相对中性 | 可在相关工作中使用 |

**我推荐的最终题目**是：**基于 H&M 交易数据与商品属性层次图的周级服装属性趋势预测与轻量 Top-N 推荐**。这个题目兼顾了数据来源、方法对象、主任务与应用任务，答辩时也更不容易被“你这哪里是知识图谱”“你这只是推荐没做趋势”之类的问题卡住。

## 数据集适配性分析

这个数据集适合你，理由不是因为它“是一个知名 Kaggle 比赛”，而是因为它恰好兼具三个必要条件：第一，`transactions_train.csv` 里有按日期排序的真实交易记录，可做周级时间切分；第二，`articles.csv` 提供了比较丰富的商品分类与属性字段，可做属性聚合和图构建；第三，官方任务本身就是未来 7 天 Top-N 购买预测，与你计划的轻量推荐目标一致。公开复现仓库普遍把它视为一个由 `articles`、`customers`、`transactions_train` 三张主表组成的大型时序推荐问题；交易跨度约两年，规模约 137 万用户、10.5 万商品、3178 万交易。

| 数据表 | 你应如何使用 | 进入主模型的程度 | 备注 |
|---|---|---|---|
| `transactions_train.csv` | 构造周级销量、热度、用户历史、候选集、评测标签 | **核心** | 主时序表 |
| `articles.csv` | 构造属性层次图、属性趋势、内容相似度与可解释展示 | **核心** | 最有研究价值的一张表 |
| `customers.csv` | 做用户分组、冷启动 fallback、统计分析 | **辅助** | 不宜全部硬塞进主模型 |

| 字段 | 建议用途 | 是否适合趋势预测 | 是否适合推荐 | 备注 |
|---|---|---|---|---|
| `t_dat` | 周切分、滚动窗口、标签构造 | **是** | **是** | 最关键时间字段 |
| `customer_id` | 用户历史、召回候选、评测分组 | 否 | **是** | 主键 |
| `article_id` | 商品级信号、Top-N 输出 | **是** | **是** | 主键 |
| `price` | 折扣代理、价格带统计 | 可选 | 可选 | 更像相对价格，不适合做经济学解释 |
| `sales_channel_id` | 线上/线下偏好、渠道统计 | 可选 | 可选 | 更适合补充特征，不是主线 |
| `product_code` | 缓解 article 稀疏、作为 article 与 category 中间层 | **是** | **是** | 很值得加进图中 |
| `prod_name` | 展示案例、人工解释 | 否 | 否 | 不建议当核心特征 |
| `detail_desc` | 文本关键字抽取、扩展图 | 可选 | 可选 | 有余力再用 |

关于交易字段的几个关键细节，公开复现资料与 Kaggle 页面说明是一致的：官方目标是预测训练期结束后未来 7 天的购买；`transactions_train` 中重复行可能表示同一商品的多次购买；`price` 值被处理过，不适合做真实货币解释；`sales_channel_id` 可区分门店与线上渠道。

客户画像字段不应“一股脑儿”进入主模型。公开 EDA 普遍发现：`age` 与 `fashion_news_frequency` 可用但会有少量缺失；`FN` 与 `Active` 缺失严重；`postal_code` 虽然通常完整，但高基数、可解释性弱，且有 notebook 观察到某些编码聚集异常。再加上公开方案里，`age` 更常被用来做冷启动热门商品 fallback，而不是作为复杂用户表示学习的核心输入。因此，本科毕设里最稳妥的做法是：`age` 可以保留，`club_member_status` 与 `fashion_news_frequency` 可做弱特征，`FN`、`Active`、`postal_code` 不进入主模型。

| 客户字段 | 是否建议进入主模型 | 推荐用法 | 不推荐原因 |
|---|---|---|---|
| `age` | **谨慎建议** | 年龄分桶、冷启动 fallback、用户偏好统计 | 不宜做过强个性化假设 |
| `club_member_status` | 可选 | 弱类别特征 | 与真实时尚偏好关系未必稳定 |
| `fashion_news_frequency` | 可选 | 营销触达倾向弱特征 | 噪声较大、解释力有限 |
| `FN` | **不建议** | 最多做描述性统计 | 缺失重、语义不清 |
| `Active` | **不建议** | 最多做描述性统计 | 缺失重、语义不清 |
| `postal_code` | **不建议** | 除非只做粗粒度分桶实验 | 高基数、位置代理变量、解释风险高 |

## 商品属性层次图设计建议

这部分建议你采用**“骨干层级 + 侧向属性分支”**的设计，而不是硬把所有字段塞成一棵绝对严格的树。因为这个数据集里的字段并不都是纯粹的父子层级，有些更像平行视角下的 merchandising 标签。最稳妥的定义方式是：先拿几组明显有层次关系的字段构成骨干，然后把颜色、图案、部门等字段作为 article 的属性分支接到图上。时尚领域相关工作已经证明，属性节点不仅有利于解释，还可以作为 item 之间的信息桥梁。

| 字段 | 在图中的角色 | 是否适合做骨干层级 | 是否建议保留 | 说明 |
|---|---|---|---|---|
| `index_group_name` | 最上层人群/业务大类 | **强** | **保留** | 适合做 top-level group |
| `index_name` | 次级业务线 | **强** | **保留** | 常与 section 搭配形成较清晰层次 |
| `section_name` | 中层分类 | **强** | **保留** | 非常适合周趋势解释 |
| `garment_group_name` | 中下层服装组 | **强** | **保留** | 适合连接到 `product_type_name` |
| `product_type_name` | 叶子级或近叶子级类别 | **最强** | **保留** | 你要重点建模的类别层 |
| `product_group_name` | 较粗商品组 | 中等 | **保留，但不强行入骨干** | 更适合作为平行粗粒度属性 |
| `graphical_appearance_name` | 图案/视觉风格属性 | 否 | **强烈保留** | 适合做 style/pattern 趋势 |
| `colour_group_name` | 颜色细分 | 否 | **保留** | 建议与 master/value 配合 |
| `perceived_colour_master_name` | 颜色主类 | 否 | **强烈保留** | 颜色趋势最稳的一层 |
| `perceived_colour_value_name` | 明暗/深浅感知 | 否 | 保留 | 适合做辅助颜色属性 |
| `department_name` | 商业组织/部门标签 | 弱 | 保留为平行边 | 不建议硬塞进主树 |
| `detail_desc` | 文本说明 | 否 | 有余力再用 | 适合做增强图，不适合最小可行版 |

| 方案 | 节点类型 | 边类型 | 适用场景 |
|---|---|---|---|
| 最简图 schema | `article`、`product_code`、`product_type`、`garment_group`、`section`、`index`、`index_group`、`colour_master`、`graphical_appearance` | `belongs_to`、`has_color`、`has_pattern` | **本科最稳妥版本** |
| 增强图 schema | 在最简图基础上增加 `colour_group`、`colour_value`、`department`、`product_group`、`keyword(detail_desc)`，以及 `item-item` 的 `co_purchase`/`similar_attr` 边 | `belongs_to`、`has_attr`、`co_purchase`、`similar_to` | 有余力做更完整实验时 |

我建议你在论文里明确写成下面这种表述：

> 本文构建的是**商品属性层次图**。该图以商品分类链路作为骨干，以颜色、图案等属性作为侧向分支；当引入多类型节点和多类型边时，可进一步视为一种**商品属性异构图**。考虑到本研究未引入外部本体、实体链接和大规模三元组知识库，因此不将其严格称为知识图谱。

这种写法最稳。真正的 fashion KG 工作通常会强调实体链接、外部知识引入、海量 triples 与 ontology；你这个题目没必要为“KG”二字背太多答辩成本。

## 周级趋势定义与趋势感知推荐关系

趋势定义是这个课题最重要的学术锚点。时尚趋势文献里，比较有代表性的做法并不是死盯单个 SKU，而是预测**style、attribute、category 这类更稳定单元的未来流行度**；也有工作明确把产品属性时间序列作为流行度代理来建模。与之相比，直接对 article 级别做周销量预测虽然最直观，但会受到严重稀疏性和噪声影响。TrendRec 进一步指出：如果你的目标是“推荐下一时间步最值得关注的趋势项”，那么只用 RMSE 这类数值误差并不对齐任务目标，top-K 趋势识别更关键。

下文记 `c_{i,t}` 为商品 `i` 在第 `t` 周销量，`h_{a,t}` 为属性 `a` 在第 `t` 周热度，`K` 为你关心的热门属性个数。

| 趋势标签方案 | 公式 | 所需字段 | 优点 | 缺点 | 是否适合本科毕设 | 推荐程度 |
|---|---|---|---|---|---|---|
| 商品级未来一周销量 | `y_{i,t}=c_{i,t+1}` | `t_dat, article_id` | 最直观；和推荐目标一致 | 极稀疏；长尾几乎全 0 | 中等 | ★★ |
| 商品级增长率 | `y_{i,t}=log((c_{i,t+1}+1)/(c_{i,t}+1))` | `t_dat, article_id` | 能抓“突然变热” | 低销量商品极不稳定 | 中等 | ★★ |
| 属性级热度增长 | `y_{a,t}=log((h_{a,t+1}+1)/(h_{a,t}+1))` | `t_dat + 属性字段` | 密度更高；更可解释；可直接接图 | 依赖属性粒度设计 | **高** | **★★★★** |
| 属性级热度加速度 | `y_{a,t}=(h_{a,t+1}-h_{a,t})-(h_{a,t}-h_{a,t-1})` | `t_dat + 属性字段` | 更接近“正在起势” | 噪声较大，需平滑 | 中高 | ★★★ |
| 层级 Top-K 热门属性预测 | `label(a,t)=1[a∈TopK(h_{a,t+1})]` 或 `TopK(y_{a,t})` | `t_dat + 属性字段` | 与排名指标天然对齐；答辩直观 | 丢失连续值信息 | 高，适合做辅助任务 | ★★★ |

如果只选一个**主标签**，我建议选：**属性级热度增长**，且最好对 `h_{a,t}` 先做轻度平滑，例如 EWMA 或 2 周移动平均，然后再计算增长。这样比“原始 article 级周销量”更稳，也更容易解释“为什么这周是某种颜色、某种款式在升温”。如果你还有余力，可以把“属性级热度加速度”做成扩展实验，用来说明你也考虑了“正在变热”而不是只是“已经很热”。

| “趋势预测”和“推荐”的关系 | 优点 | 缺点 | 本科适配性 | 我的判断 |
|---|---|---|---|---|
| 先趋势预测，再推荐 | 论文主线清晰 | 推荐可能显得偏弱 | 高 | 可行 |
| 趋势作为推荐特征 | 简单稳妥；最容易落地 | 趋势模块存在感可能不够强 | **最高** | **推荐** |
| 趋势作为重排序因子 | 直观、可解释，适合答辩 | 需要先有候选集 | **最高** | **推荐** |
| 联合训练趋势预测和推荐 | 看起来“高级” | 复杂、难复现、难排错 | 低 | 不建议 |

因此，我的明确建议是：**独立训练趋势预测模块，然后把趋势分作为推荐特征或重排序因子使用**。这比“端到端联合训练”更容易讲清楚，也更符合本科毕设的风险控制逻辑。

## 推荐任务设计、时间划分与评价

推荐模块不需要做成工业级大系统，但也不能只做“全站热门榜”就结束。公开比赛经验非常清楚地说明了两件事：第一，这个数据规模下，全量用户-商品打分会爆炸；第二，recent popularity 在时尚场景里非常强，但单靠它又容易陷入热门偏置。比较稳妥的做法是：**小而精的候选集召回 + 轻量重排序**。公开方案里，有的只保留 50 个左右候选，有的生成 400 个候选再用 LightGBM 排；还有方案明确使用最近一周共购候选与按年龄分组的热门商品作为冷启动补全。

| 方法 | 难度 | 算力 | 可解释性 | 作为 baseline | 作为最终方法 | 建议 |
|---|---|---|---|---|---|---|
| Popularity | 很低 | 很低 | 高 | **必须有** | 否 | 必做 |
| Recent Popularity | 很低 | 很低 | 高 | **必须有** | 可作为强基线 | 必做 |
| Item-CF | 低 | 低到中 | 高 | **强烈建议** | 可做最终召回之一 | 必做 |
| User-CF | 中 | 中到高 | 一般 | 可对比 | 不建议主用 | 不推荐主线 |
| MF / BPR | 中 | 中 | 中 | 建议保留一个 | 可做补充 baseline | 建议 |
| LightGCN | 中到高 | 中到高 | 中 | 可做“高级 baseline” | 不建议当主线 | 有余力再做 |
| LightGBM Ranking | 中 | 中 | **较高** | 可不用作 baseline | **最适合最终轻量排序** | **推荐** |
| 双塔模型 | 高 | 中到高 | 中 | 无必要 | 不推荐 | 反对 |
| 图神经网络 | 高 | 高 | 中 | 无必要 | 不推荐 | 反对 |

这个判断背后有非常直接的依据。经典 item-to-item CF 在工程上以可扩展著称；BPR 针对隐式反馈的个性化排序任务提出了直接优化排名的目标；LightGCN 虽然比传统 GCN 简洁很多，但仍然需要图训练与 embedding 调参；LightGBM Ranker 则天然支持 `lambdarank` 目标；双塔与工业检索模型更适合“大规模候选检索”，而不是本课题这种“解释优先、论文优先”的本科毕设。

| 推荐任务问题 | 建议答案 |
|---|---|
| 是否做 Top-N 推荐 | **做** |
| 推荐列表长度是否采用 12 | **采用 12**，与官方任务一致 |
| 是否沿用 MAP@12 | **沿用，作为主指标** |
| 是否需要预测所有用户 | 代码上可为所有用户生成；**评测时只统计测试窗口有购买的用户** |
| 是否只评估测试窗口有购买记录的用户 | **是**，这与官方评分逻辑一致 |
| 是否做候选集召回 + 重排序 | **建议做轻量两阶段** |
| 候选集大小 | 推荐 100–300；若只做 heuristic，可控制在 50–150 |
| 候选来源 | 用户最近购买、Item-CF、近期热门、趋势属性映射商品、可选年龄段热门 |

官方竞赛与公开讨论都强调：评分只针对测试窗口内有购买行为的顾客；没有未来购买的顾客不纳入 scoring。这意味着你在论文里**不要把没有正样本的用户硬算成“推荐失败”**。另外，由于 Kaggle 真正测试标签是隐藏的，论文实验必须建立在 `transactions_train` 尾部切出的**本地伪测试集**上，而不是拿 leaderboard 当论文证据。

| 时间划分步骤 | 安全做法 | 常见泄漏点 |
|---|---|---|
| 定义周窗口 | 先把全部交易映射到 ISO 周或自定义周序号 | 直接按随机样本切分 |
| 训练集 | 仅使用截止周 `T` 及之前的全部数据 | 用到 `T+1` 周统计过的热门度 |
| 趋势标签 | 用 `T+1` 周的销量/热度构造标签 | 用全局归一化或全时段统计参与标签计算 |
| 用户特征 | 截止到 `T` 的历史购买、最近购买时间、类目偏好 | 把验证周或测试周购买带入特征 |
| 商品/属性热度 | 截止到 `T` 的滚动统计、移动平均、增长率 | 用全期统计值做“历史热度” |
| 候选集 | 仅由 `T` 之前行为召回 | 用 `T+1` 的共购关系做候选 |
| 评测 | 在 `T+1` 周真实购买上计算指标 | 把无未来购买的用户强行纳入 MAP |
| 验证方式 | 最好做最后 4–8 周 rolling weekly backtest | 只切一次且恰好碰到某个异常周 |

在时间感知推荐里，按时间切分训练/测试本来就是更贴近真实部署的做法；相关教程也明确指出，工业推荐系统的训练-评估通常应按时间边界 `T` 前后切分。你的论文只要严格坚持“任何特征都不能看见 `T+1`”，就能基本避免时间泄漏。

| 任务 | 指标 | 我建议的定位 |
|---|---|---|
| 趋势预测 | MAE / RMSE | **仅在你预测连续销量时做辅助指标** |
| 趋势预测 | Spearman | **推荐保留**，用于看趋势排序相关性 |
| 趋势预测 | Precision@K / Recall@K / NDCG@K / HitRate@K | **主指标**，若你关心“识别下周热门属性” |
| 推荐 | MAP@12 | **主指标**，与官方一致 |
| 推荐 | Recall@12 | **次主指标**，对答辩很友好 |
| 推荐 | NDCG@12 | **推荐保留**，体现排序质量 |
| 推荐 | HitRate@12 | **推荐保留**，直观 |
| 推荐 | Coverage / Novelty / Long-tail Coverage | **论文增色指标**，用来避免“只是热门榜” |

TrendRec 的一个很重要的提醒是：如果目标是推荐下一时间步的 trending items，那么只看 RMSE 这类点误差并不对齐，top-K 趋势识别能力更关键。对你的课题来说，这几乎可以直接转化成一个论文策略：**趋势预测任务用 rank-aware 指标为主，推荐任务继续用 MAP@12 为主**。

## 方法路线、实验方案与最终交付

如果把你的课题放在“本科可交付”的约束下，我最推荐的路线不是 A 也不是 D，而是**C 的轻量版本**：趋势预测和推荐都做，但不端到端联合；趋势预测是论文主贡献，推荐是趋势模块的验证与应用。这样既有完整性，又不会把自己拖进模型黑洞。

| 路线 | 难度 | 创新性 | 复现性 | 算力要求 | 答辩友好度 | 论文完整性 | 风险 | 判断 |
|---|---|---|---|---|---|---|---|---|
| A 趋势预测主任务，推荐作应用展示 | 低 | 中 | 高 | 低 | 高 | 中高 | 推荐部分偏弱 | 可行 |
| B 推荐主任务，趋势作特征 | 中 | 中 | 高 | 中 | 高 | 高 | 趋势模块存在感不足 | 可行 |
| C 双任务但不端到端联合 | 中 | **中高** | **高** | 中 | **最高** | **最高** | 需要严格实验组织 | **最推荐** |
| D 复杂端到端联合模型 | 高 | 表面高 | 低 | 高 | 低 | 中 | 训练、排错、解释都难 | 不建议 |

| 模块 | baseline 建议 | 最终方法建议 |
|---|---|---|
| 趋势预测 | Last Week、Moving Average、EWMA、简单线性回归/LightGBM lag features | **属性级趋势预测：EWMA + LightGBM Regressor/Classifier** |
| 推荐召回 | Global Popularity、Recent Popularity、Item-CF | **Recent Popularity + Item-CF + 趋势属性映射候选** |
| 属性图增强 | 无图版本、仅类别骨干、骨干+颜色、骨干+颜色+图案 | **用图把属性趋势传播到 item 分数，而不是上来就 GNN** |
| 推荐排序 | 线性加权打分 | **LightGBM Ranker 或可解释线性重排序** |

一个非常稳妥的最终方法，可以写成下面这条主线：

1. 以周为单位聚合交易，计算 article 与 attribute 的历史热度序列。  
2. 用 `index_group / index / section / garment_group / product_type / product_code / article` 构造分类骨干，用颜色与图案做属性分支。  
3. 在属性节点上预测未来一周趋势分。  
4. 将趋势分映射回商品：  
   `trend_score(i)=Σ_{a∈A(i)} w_a * ŷ_a`  
5. 用“用户历史偏好 + Item-CF + recent popularity + trend_score”组成候选和排序特征。  
6. 输出 Top-12，评测 MAP@12、Recall@12、NDCG@12，并报告 coverage 与 long-tail coverage。  

这种方法很像把图当作“**结构化聚合器**”，而不是把图神经网络当作“必须上”的深模型。它非常适合本科答辩。

| 实验模块 | 你应该怎么做 | 目的 |
|---|---|---|
| 时间滚动验证 | 取最后 4–8 个周窗口做 rolling backtest | 稳定结果，避免单周偶然性 |
| 趋势预测实验 | 比较 Last Week / MA / EWMA / LightGBM | 证明趋势模块本身有效 |
| 推荐实验 | 比较 Popularity / RecentPop / Item-CF / BPR / Trend-aware 重排 | 证明趋势能给推荐带来增益 |
| 消融实验 | 去掉图、去掉趋势、去掉颜色、去掉图案、去掉年龄 fallback | 证明每个设计环节是否必要 |
| 长尾分析 | 统计 long-tail item 的召回率与覆盖率 | 回答“是否只会推热门” |
| 冷启动用户分析 | 历史购买 0–1 次用户单独评测 | 检验 fallback 策略 |
| 属性趋势解释展示 | 展示“本周上升的颜色/图案/类目”及其对应商品 | 提升可解释性与答辩观感 |

| 风险 | 表现形式 | 规避方案 | Plan B |
|---|---|---|---|
| 数据规模大 | 处理慢、内存爆 | 先用 Parquet/分周聚合/按月缓存 | 只保留最近 6–12 个月做主实验 |
| 热门商品主导 | 指标看起来高但没个性化 | 加入 Item-CF、用户类目偏好、coverage 指标 | 至少报告 long-tail coverage |
| 趋势定义不清 | 论文主线飘 | 只设一个主标签，其他全做扩展 | 主标签固定为“属性级热度增长” |
| 周粒度过细 | 噪声大、结果跳 | 做 EWMA 或 2 周平滑 | 降为双周粒度 |
| 属性层级太复杂 | 图 schema 讲不清 | 只保留骨干层级 + 两个属性分支 | 删掉 department / detail_desc |
| 推荐模块过重 | 训练与排错失控 | 只做轻量两阶段 | 改成线性重排 |
| 只做热门推荐 | 被批评没有个性化 | 加入 Item-CF 与历史偏好分 | 至少做“用户偏好类目内热门” |
| 时间泄漏 | 线下分数虚高 | 所有特征严格截止到 `T` | 重跑整套 pipeline 做校验 |
| 客户字段噪声高 | 模型不稳定 | 客户字段只做弱特征 | 全部移出主模型 |
| 官网测试标签隐藏 | 论文无法直接用 leaderboard | 构建本地伪验证与伪测试 | 用最后 1 周做 test、前 4 周做 val |
| 与 Kaggle 不完全一致 | 指标不好对比 | 主指标仍保留 MAP@12 | 补充 Recall/NDCG 解释 |
| 创新点不足 | 像课程作业 | 把创新点放在“属性层次图 + 属性趋势 + 趋势感知重排 + 可解释性” | 强化消融与案例分析 |

这些风险并不是理论上的，而是公开方案、趋势推荐研究和大规模图训练文献都反复体现出来的问题：时尚场景 recent popularity 很强、趋势识别容易被热门偏置吞掉，而重型图训练又天然更难稳定扩展。

| 最终关键问题 | 我的明确建议 |
|---|---|
| 最终题目用哪个 | **基于 H&M 交易数据与商品属性层次图的周级服装属性趋势预测与轻量 Top-N 推荐** |
| 主任务是什么 | **属性级周趋势预测** |
| 辅助任务是什么 | **趋势感知 Top-N 推荐** |
| 商品属性层次图怎么建 | **分类骨干 + 颜色/图案分支 + 可选 product_code 中间层** |
| 趋势标签怎么定义 | **主标签：属性级平滑热度增长；扩展标签：属性级加速度** |
| 推荐模块做到什么程度 | **候选召回 + 线性/LightGBM 重排序** |
| 最小可行版本是什么 | **图骨干 + 属性趋势预测 + RecentPop / Item-CF / Trend 重排** |
| 答辩稳妥版本是什么 | **再加 rolling weekly backtest、消融、长尾分析、可解释案例** |
| 有余力可以增强什么 | `detail_desc` 关键词、年龄分群趋势、LightGCN 额外 baseline |

**开题报告可复用研究思路摘要**

本研究以 H&M 个性化时尚推荐竞赛数据为基础，面向时尚零售场景中“趋势变化快、商品长尾明显、推荐需要兼顾时效性与可解释性”的问题，提出一种“周级属性趋势预测 + 轻量 Top-N 推荐”的研究框架。首先，基于 transactions_train 的时间戳信息按周构建商品与商品属性的热度序列；其次，结合 articles 中的类别、颜色、图案等结构化字段，构建商品属性层次图，以缓解商品级销量稀疏并提供可解释的属性聚合视角；然后，围绕属性节点定义未来一周热度增长等趋势标签，建立周级流行趋势预测模块；最后，将预测得到的趋势分与用户历史购买偏好、商品属性相似度及近期热门度共同用于轻量 Top-N 推荐。实验上采用严格的时间滚动划分，分别评估趋势预测与推荐效果，并通过消融实验、长尾分析、冷启动分析和属性趋势案例展示验证方法的有效性与可解释性。整体目标不是追求 Kaggle 榜单最优，而是形成一个结构清晰、可复现、易答辩、具有一定研究价值的本科毕业设计方案。

**论文方法章节草案大纲**

1. 问题定义与任务重构：从官方 7 天购买预测重构为“属性趋势预测 + 趋势感知推荐”。  
2. 数据预处理与周级时间切分：周窗口定义、用户活跃窗口、伪验证与伪测试构造。  
3. 商品属性层次图构建：节点类型、边类型、骨干层级与属性分支。  
4. 周级趋势标签设计：商品级与属性级标签、平滑策略、主标签选定。  
5. 趋势预测模型：统计基线、移动平均、LightGBM lag-feature 模型。  
6. 趋势感知推荐模块：候选召回、趋势分映射、轻量重排序。  
7. 实验设置与评价指标：趋势任务指标、推荐任务指标、coverage 与 long-tail。  
8. 消融实验与可解释性分析：去图、去趋势、去颜色/图案、趋势案例展示。  

**你下一步应该立刻做的 5 件事**

1. **先固定题目与主线**：马上把题目收敛成“属性级周趋势预测为主、轻量推荐为辅”，不要再往“知识图谱端到端联合模型”方向发散。  
2. **先做时间切分脚本**：把 `transactions_train.csv` 转成按周索引的数据表，产出最后 8 周的 rolling validation 方案，这是后面所有实验的地基。  
3. **先画出最简图 schema**：只画 `index_group → index → section → garment_group → product_type → product_code → article`，并给 article 接 `colour_master` 与 `graphical_appearance` 两条属性分支。  
4. **先跑四个 baseline**：趋势侧跑 Last Week / MA / EWMA；推荐侧跑 Recent Popularity / Item-CF。只要这四个 baseline 跑通，你的开题和中期检查就都有底了。  
5. **先写一页“变量与标签定义”**：明确 `c_{i,t}`、`h_{a,t}`、主趋势标签、评测窗口、是否排除无未来购买用户。越早写清楚，越能避免后期时间泄漏和论文逻辑混乱。
